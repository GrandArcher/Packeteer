# Feature matrix

This matrix lists Packeteer's capabilities with their status, target milestone, the plugin kind that implements each one, the tracking issue, and whether an operator has proven it in the field.

Every feature ships as a plugin behind the interfaces in `pkg/plugin` wherever one fits (see [PLUGINS.md](PLUGINS.md)), and it must work in the stock Docker image. Packeteer's safety rules (observe by default, allowlist, community tagging, improvement cap, withdraw on failure, no graceful restart) apply to every feature.

Statuses: **done** (merged to `main`), **partial** (merged, but part of the intended behavior is missing; the row says what and links the issue), **in progress** (open PR or active branch), **planned** (issue exists), **won't do** (reason given).

Field-proven: whether an operator has reported the row working on a production edge. None has yet; reports are collected in #54. `no (lab-proven)` means a lab with real BGP daemons (FRR, GoBGP, BIRD, MikroTik CHR) proves it on simulated routers; `no` means unit and integration tests only.

Milestones:
- **v0.1**: installable core outbound performance loop: probing, targets from static lists and flows, RIB via iBGP, scoring with hysteresis, injection via GoBGP, web UI + API + metrics, Docker, e2e lab, operator quick start and config reference.
- **v0.2**: cost and commit control, SNMP, VIP and AS-pattern detection, policies (prefix/ASN/country), alerts, reports.
- **v0.3**: inbound optimization, BMP, multiple routers and IX, FlowSpec/RTBH, transit optimization.
- **v0.4**: multi-POP, HA, RBAC, anomaly detection, remaining UI and ops features.
- **v0.5**: hardening and polish on the rows above. Dashboard clarity and the first-run checklist (#49), CI-tested quickstart, walkthrough, troubleshooting, and router guides (#50), load and soak budgets and the flow-ingest fix (#51), MikroTik CHR in QEMU on CI (#52), and the router interop matrix (#53) are done. They are not new capability rows, so the counts below are unchanged. Field feedback from observe-mode deployments (#54) is still open. Lab-proven only; the safety rules above are unchanged.
- **v0.6**: gaps found in the 2026-10-07 review of prefix selection, measurement, and the UI. The partial rows say what is missing and link their issue; keeping an improved prefix probed after its source drops it is done (#116), an RTT win can also require a percent of the current path while a new performance move waits for consecutive fresh rounds (#117), the probe engine remembers which prober a host answers (#120), a host qualifies by reply count and RTT spread, with a wide spread escalated to a full probe (#119), and a flow prefix stays eligible on a byte floor or a percent of the window, with `top_n` the priority tier inside a larger capped set (#118), and the probe scheduler stores each prefix whose probes all finished, even when the round times out, while a flow sketch counts prefixes past the exact cell cap (#125). 3 new rows are planned, 1 is won't do, and leak watch is done (#199); its NLNOG RING source, RPKI-invalid flag, and `synthesize` requirement are follow-ups (#200, #122). UDP unreachable replies count only when the ICMP source is the probed target (#15). Traceroute discovery runs in the background under `budget` and does not block a probe round. VIP ASN expansion is capped by `max_targets` and rebuilt only when the RIB changes; the VIP interval must be shorter than the staleness window.

Host qualification (#119) is off at the defaults (`min_replies` 1, `dispersion_ms` 0): any reply counts, and an inconsistent sample is not probed again. With `dispersion_ms` set, a host whose slowest reply minus its fastest is wider than that limit is left out of the score and the prefix is probed again with `retry_packets`. Too few replies drop the host and do not escalate. The staleness window is `3 * interval + packets * timeout`, plus `retry_packets * timeout` only when that second probe can run. A flow prefix offers up to three of the busiest destinations in the window as candidates. This measures only. It does not announce.

Flow selection (#118) keeps a prefix when an enabled floor passes. `min_bytes` above 0 is the absolute total. `min_pct` above 0 is that percent of the bytes in the window. Either floor is enough, and a zero floor is off. With both at zero every prefix with bytes is eligible and `top_n` still cuts the list, which is the previous behavior. `top_n` is probed every round. `max_targets` (default `top_n`, at most 10000) is the larger set; prefixes past `top_n` carry `tail_interval`, which must be longer than `probe.interval` and shorter than the staleness window. Problem prefixes stay on the normal interval. Every packet still waits on `probe.rate_limit_pps`. This measures only. It does not announce. Defaults reproduce the previous list.

The `outage` source (#16, #124) correlates probe results inside `window` (default 2m). An ASN incident needs `min_prefixes` (default 3, minimum 2) degraded prefixes that cross that ASN and are degraded on every measured provider. The ASN can sit on the native AS path, on another provider's learned path (add-path or BMP), or be the origin ASN of a traceroute hop. A hop address maps to the last ASN of the longest matching learned prefix; a default route is not a match, and no external data is used. Hops come from per-provider indirect traces when a trace is cached.

A prefix that is still healthy on another provider does not count toward that rule unless the ASN appears only on the degraded provider's path, in which case the incident is attributed to that provider and is not also a circuit. A provider incident is the same count of prefixes degraded on that provider and healthy on another, and not already explained by a sick ASN. One noisy prefix does not fire. With no traces and no alternate paths the correlation is the native AS path alone. The probe loop wakes and re-queues the affected prefixes, including other learned prefixes that cross the sick ASN, capped by `max_targets`.

Events go to the configured notifiers. The source does not announce.

Passive problem detection (#21) feeds probing; it never announces. The `span` source reads a mirror port with AF_PACKET (`NET_RAW`, host networking) or replays a classic pcap, follows TCP connections between the configured `local` networks and remote addresses, and scores each remote prefix by outbound retransmissions, handshake timeouts, remote resets, and optionally handshake RTT. The `flow` source's optional `problems` block does the same from TCP flags on unsampled NetFlow v5/v9 and IPFIX records (SYN without ACK outbound, RST inbound); retransmissions and RTT are not visible in flow records, and sampled exports and sFlow are skipped. Problem prefixes are probed first; injection still needs the learned RIB, allowlist, thresholds, cap, community, and hold time. Tests use a synthetic pcap fixture with documentation prefixes and, in CI, a root-only AF_PACKET capture on loopback. Removing the source (or the `problems` block) and restarting is the rollback.

Flap quarantine (#228, [CONFIG.md](CONFIG.md#flap_quarantine)) is on by default and only withdraws. Each new improvement, switch, and flip-back of a prefix is one change. A change that would be more than `max_flips` inside `window` is not made: the route is withdrawn (or never announced) and the prefix stays on the native path for `cooldown`, doubled for each repeat offense within `max_cooldown` of the last release and capped at `max_cooldown`. It applies on top of `hold_time`, `confirm_rounds`, the cap, and the allowlist, and blocks every cause, static pins included. State is in memory, so a restart clears it. Lab-proven only (`lab/e2e-flap.sh`). Rollback: `flap_quarantine: {disabled: true}`.

The `snmp` telemetry plugin (#17) polls `ifHCInOctets` and `ifHCOutOctets` (32-bit octet counters when the 64-bit ones are absent). The community and v3 passphrases are environment variables named in the config, not values in the file. Samples stay in memory for the open UTC billing period (`billing_day` 1-28). When a storage plugin is configured (#127), each accepted sample is written per binding and billing period and the open period is loaded on start, so the 95th matches across a restart. Without storage a restart clears the window. A closed period stays in the database until `retention` deletes it.

`max_samples` still caps the open period in memory, and the stored open period is trimmed to that cap. Backup and restore include the samples. The 95th percentile is nearest rank, ceil(0.95 x N). `separate` keeps the inbound and outbound 95ths apart. `greater` is the 95th of max(in, out) on each sample. `greater_separate` is the greater of those two 95ths. The numbers are on `/api/telemetry` and `packeteer_telemetry_*`. The plugin does not announce. Commit control still needs a fresh reading and still goes through Decide.

The `commit` scorer (#18) is off unless `scorer.type` is `commit`. Its performance score matches `weighted`. When telemetry has a fresh billable 95th (`usage_mbps`, or the outbound 95th when the mode is `separate`) and a source reports per-prefix volume (the flow window, or `mbps` on a static target), it moves prefixes off a provider that is over `commit_mbps` onto one with room for that volume. A move that would increase loss is refused unless `loss_override` is set, and Decide refuses that move even if another planner emits it. A move onto the native provider is not a steer.

An active commit steer whose loss exceeds the native path by `min_loss_delta_pct` is withdrawn at once and waits out `hold_time` before it can return; a smaller gap stays. `cc_disable` leaves a provider out of these moves. `balance` `equal` or `proportional` balances providers that share `group`; `off` only relieves over-commit. `precedence` (lower is preferred, omitted means 100) orders relieve destinations ahead of group membership, and the highest precedence is used only when every lower one lacks room. Each improvement is tagged `performance` or `commit` and counts toward `max_improvements`. Equal relief breaks by prefix.

A new performance move displaces the smallest commit steer when the cap is full, and that prefix takes a cooldown. Performance volume is passed to the planner as locked so it is not commit-steered as well. The prefix must be in the learned RIB. Volumes are read only when the scorer plans. Switching the scorer back to `weighted` and restarting withdraws commit improvements. Observe stays the default. The FRR lab's commit job announces a commit-cause route, withdraws it when the usage file drops under commit, and checks SIGTERM and SIGKILL.

The `cost` scorer (#19) is off unless `scorer.type` is `cost`, and needs `providers[].cost` (price per Mbps) on at least two non-excluded providers. Its performance score matches `weighted`. It moves a prefix to the cheapest priced provider whose path is inside `floor`: at most `max_loss_pct` (default 0) above the lowest loss and `max_rtt` (default 10ms) above the lowest RTT among usable, non-excluded providers. The destination must be cheaper than native.

Decide re-checks the floor and the price for every cost move, withdraws an active cost steer at once when it leaves the floor (with a `hold_time` cooldown), and applies the RIB, allowlist, cap, and cooldown rules. `precedence: performance` (default) lets performance moves win; `precedence: cost` keeps a native path inside the floor and, when native is outside it, prefers the cheapest path inside the floor over the fastest one. Improvements are tagged `cost`. `cost_delta` and `est_savings` (price difference times prefix volume) are on `/api/improvements`, and `packeteer_estimated_savings` sums them; the full savings report is #23.

The cost scorer does not do commit control. Switching back to `weighted` and restarting withdraws cost improvements. Observe stays the default. The FRR lab's cost job announces a cost-cause route, withdraws it when the cheap path leaves the floor, and checks SIGTERM and SIGKILL.

| Inbound performance optimization (prepends, provider TE communities, selective announcements) | done (lab-proven only) | v0.3 | announcer (inbound `gobgp`, `withhold` action) + core (`internal/inbound` performance trigger) | #25 | no (lab-proven) |

Inbound optimization (#25) steers inbound traffic for the operator's own `inbound.prefixes` away from a provider. Two triggers: **commit**, when the provider's inbound 95th percentile (telemetry) is above its commit, and **performance** (`inbound.performance`), when the probes rank it the single worst provider by mean loss or RTT over the prefixes every provider measured.

In `inject` the in-process inbound `gobgp` announcer re-announces the exact learned prefix and next hop to the edge with `packeteer_community`, a marker community, the provider's catalog communities (a prepend signal the edge maps to `set as-path prepend` on that session, a `withhold` signal the edge maps to not exporting to that provider at all, i.e. a selective announcement, and the provider's own TE communities), and NO_EXPORT; the edge's import policy opts in ([inbound.md](inbound.md)). `observe` (default) logs.

Moderated vs automated: `suggest`, and any trigger listed in `inbound.moderated` while in `inject`, publish on `/api/inbound` and as `inbound.steered` events and announce nothing; the rest are automated. Damping (`inbound.damping`, on by default) confirms a trigger before steering, grows the hold time and cooldown of a flapping provider by `backoff` up to `max_hold`, and learns inertia (the inbound traffic that returned on the last release) so a commit steer is released only when demand really drops; a unit simulation shows about 140 undamped changes a day falling to four.

Steers are held, released at `release_pct` (commit) or `performance.release_pct`, retired at `improvement_ttl`, released at once on stale telemetry or missing probe results (probe-source loss), withdrawn on RIB loss and shutdown, share `max_improvements` with outbound, never cover every provider, and never use a prefix outside the allowlist or the learned RIB.

The FRR lab (`lab/e2e-inbound.sh`) checks on the transits: the commit prepend and TE community on transit-a only, release, a damped re-steer that inertia keeps past its hold, SIGTERM withdraw, a performance steer and release, a selective announcement that removes the prefix from transit-b only, and SIGKILL. Lab-proven only, not on a public edge.

## Transit

Transit traffic optimization (#29) optimizes egress for traffic that crosses the network from customers, not only traffic the operator sources. The `flow` source's `transit` block lists the customer source networks (`customers`); each flow record (NetFlow v5/v9, IPFIX, sFlow) is transit when its source is inside them and local otherwise, and a prefix whose transit byte share over the window reaches `share_pct` (default 50) is a transit prefix.

The controller passes the class to the policy chain before each decision (`PolicySubject.Traffic`), and `rules` with `traffic: transit` or `traffic: local` give the two classes separate policies (allow/deny providers, ignore, static, vip), alone or combined with prefixes, ASNs, or countries. Classification does not add targets and never announces; the allowlist, learned-RIB check, community and NO_EXPORT, `max_improvements`, hold time, and withdraw on probe-source loss, stale data, RIB loss, and shutdown are unchanged, and an unclassified prefix matches no traffic rule.

Unit tests replay simulated NetFlow v5, IPFIX, and sFlow exports (documentation prefixes) through classification, and a controller test runs the classes through the policy chain into `Decide` in inject mode (transit restricted to its allowed provider, local on the fastest, nothing outside the allowlist or the learned RIB, both withdrawn on RIB loss). No new announce path, so no new lab script. Rollback: remove `transit` and the `traffic` rules.

Routing policies (#20) are `policy` plugins, a filter chain in front of the scorer. The `rules` policy matches a probed prefix by prefix (equal or more specific), by the origin ASN of the learned AS path, or by country from a MaxMind-format database the operator mounts (none is shipped). A prefix match beats an ASN match, which beats a country match; the longest rule prefix wins, then list order.

`ignore` retires and blocks improvements, `allow` and `deny` restrict where a prefix may be steered (never the native provider), `static` pins a provider while its path is usable and inside the rule's required `max_loss_pct` (and optional `max_rtt`), and not lossier than native by `min_loss_delta_pct` (cause `static`, checked before announce and every round while held, withdrawn with a `hold_time` cooldown when the path fails or leaves the ceiling, an existing improvement is switched onto the pin only after `hold_time`, retired at `improvement_ttl` without a cooldown), and `vip` ranks performance moves ahead when the cap binds.

The `maintenance` policy excludes providers during cron-scheduled, one-off, or on-demand (`POST /api/maintenance` with a duration or a start and end, basic auth required, in memory) windows: improvements on them are retired and no performance, static, commit, or cost move may land on them. Native traffic through the provider is not moved. Every verdict goes through Decide, so the RIB, allowlist, cap, community, and withdraw rules still hold. Removing `policies` and restarting is the rollback. Observe stays the default.

IXP mode (#160, [design](design/ixp.md)) is `ixp: {}`, for an exchange operator. It is not an edge network's `exchanges` peers. Validation refuses `mode: inject`, `announcer`, `mitigation`, `inbound`, `synthesize`, and `more_specific`. No `bgp.neighbors` and no RIB view are required. Route-server data is a separate read-only store and does not feed the RIB view or Decide. Rollback: remove `ixp` and restart.

IX-F member import (#161) is `ixp.members` with `type: ixf`. It GETs IXP Manager's `/api/v4/member-export/ixf/1.0` (or a subdirectory path that ends with that suffix) or one named IX-F JSON URL. The API key is `PACKETEER_IXP_MANAGER_API_KEY`, sent only as `X-IXP-Manager-API-Key`. This import sends it only to the manager URL. A URL that contains the key, including a percent-encoded form, is refused. `key_expires` is required when the key is set. `refresh` is 1m to 24h (default 15m) and `max_bytes` defaults to 8 MiB. `GET /api/ixp/members` serves the list. It is not the RIB and not an input to Decide, and nothing is announced. Rollback: remove `ixp.members` and restart.

Fabric probes (#162) are `ixp.vantages` plus `ixp.fabric` with `type: icmp`. Each vantage is an IX-owned address on one peering LAN. The prober measures loss, RTT, and jitter to member addresses on that LAN. Connection states other than `active`, `connected`, and `operational` are not probed. Can Ping off is not probed: IX-F `can_ping: false`, or a customers-document host whose service does not `use` `ixp-manager-member-ping-service` (busy: `ixp-manager-member-ping-busy-service`). The busy template uses the looser warning. The list is `GET /admin/api/v4/nagios/customers/{vlanid}/4` or `/6` on the same IXP Manager origin as the member export, and only then. A failed fetch keeps the last successful list for three intervals, then that VLAN is not probed. With no successful list, that VLAN is not probed. `GET /api/ixp/probes` serves the round. It is not an input to Decide, and nothing is announced. Rollback: remove `ixp.vantages` and `ixp.fabric`, or the `ixp` block, and restart.

PeeringDB / IX-F lookup (#153) is the top-level `lookup` block with `type: peeringdb`. For each configured exchange it GETs the PeeringDB `ix`, `netixlan`, `net`, and `org` objects, and an optional IX-F 1.0 member document, into an in-memory cache. `GET /api/lookup` serves the organization and network name per ASN, each member's LAN addresses, route-server participation, policy, and `info_prefixes4`/`info_prefixes6`. It sends only GETs, at least 3 seconds apart (2 seconds with a key), and never follows a redirect. The key is `PACKETEER_PEERINGDB_API_KEY`, sent only as an `Authorization` header to `base_url`; without it the lookup is anonymous and rate-limited by PeeringDB. It is display only: not the RIB, not an input to Decide, and nothing is announced. Rollback: remove `lookup` and restart.

Route-server observability (#164) is `ixp.routeservers` with `type: birdseye`. It GETs Birdseye's `api/status`, `api/protocols/bgp`, `api/routes/count/protocol/{protocol}`, and `api/routes/lc-zwild/protocol/{protocol}/{rs-asn}/1101` on each route server, without a key, and keeps per-session history (288 samples in memory) of state, received, accepted, filtered, filtered-by-reason, and `max_prefix`. Events: `ixp.rs_unreachable`, `ixp.rs_session_down`, `ixp.rs_max_prefix`, and `ixp.rs_filtered`, each with a resolving event. `GET /api/ixp/routeservers` serves the latest poll and `GET /api/ixp/routeservers/history` one session's samples. It is not an input to Decide, and nothing is announced. Rollback: remove `ixp.routeservers` and restart.

Fabric incident correlation (#163) is `ixp.correlate` with `type: topology`, and needs `ixp.fabric`. It groups each fabric round by switch, colo, and `bundles` (operator-named lists of IX-F switch ids; IX-F has no core bundle). Events: `ixp.fabric_degraded` when at least `min_members` members and `degraded_pct` percent of the members measured behind one group are past the ping tolerance for `rounds` rounds, and `ixp.member_degraded` for one member that is degraded in no such group, each with a resolving event. `GET /api/ixp/correlation` serves the evaluation. It sends no probes and no requests, is not an input to Decide, and nothing is announced. Rollback: remove `ixp.correlate` and restart.

Multi-site fabric health (#167) joins one IXP-mode instance per site with the top-level `federation` block. Each site publishes, in its mTLS snapshot, the fabric round reduced to the worst address per member, VLAN, vantage, and family, its vantages, the correlator's groups, how many route servers do not answer, and its core links. `ixp.core` (`type: icmp`) with `ixp.core_links` pings the other sites' addresses and records loss, RTT, and jitter. `GET /api/ixp/sites` and `/ixp/sites` show each site's health and where each incident is: a fabric group, a vantage, the route servers, a degraded core link (listed at the site that measured it, with the far end as `peer`), or a site with no fresh snapshot. For that last case the core link other sites measure to it says whether the site or the core is down, or only its instance or federation. A peer's stale data is not used. The site view is read-only: it pushes nothing to a site. Not built: events or notifications for site incidents. Rollback: remove `ixp.core` and `ixp.core_links`, or `federation`, and restart.

Leak watch (#199, [leak-watch.md](leak-watch.md)) is off unless `leak_watch.enabled: true`, which needs `packeteer_community` and a source. A leak source reports routes seen outside the iBGP sessions; a sighting that carries `packeteer_community` (or, with `as_path_rule`, shows an injected prefix with `asn` in its path) withdraws that one outbound route at once (never in bulk), holds the prefix out of outbound improvements and inbound steers until `POST /api/leaks/clear`, and emits `leak.detected`. Sources: `bmp` (post-policy Adj-RIB-In of routers outside the AS and Adj-RIB-Out of your own edge toward eBGP) and `rislive`. The export deny for customer, peer, and transit sessions, standard and large communities, is per vendor in [routers.md](routers.md#export-filters-on-every-ebgp-session) (#210).

A source that is down is unknown and never blocks a withdraw. Not built: the NLNOG RING looking glass as a source, the RPKI-invalid flag (needs #200), and the `synthesize` requirement (needs #122, which must reject `synthesize` without `leak_watch`). An inbound steer is held and removed at the next inbound sync. Threat mitigation routes are reported, not withdrawn. The FRR lab (`lab/e2e-leak-watch.sh`) runs a clean pass with no false positive, then a misconfigured export that leaks one of two injected routes: only that route is withdrawn and it stays out until cleared; a lost BMP feed reads unknown; SIGTERM and SIGKILL withdraw.

Lab-proven only, not on a public edge. Rollback: `enabled: false` and restart.

Online reconfiguration of core settings (#128) applies on SIGHUP and on `PUT /api/config` when every change is online. Thresholds, `hold_time`, `improvement_ttl`, `max_improvements` (including 0, which retires every improvement), policies, sources, probe timing (`interval`, `timeout`, `packets`, `retry_loss_pct`, `retry_packets`), `mode`, `allowlist`, and `bgp.neighbors` take effect on the next decision. A still-valid improvement stays up. Lowering the cap retires the lowest-ranked improvements inside `hold_time` with no cooldown (planned, then performance, then VIP, then static pins; smallest gain first). Leaving inject withdraws at once.

Shrinking the allowlist retires a prefix that is no longer covered. An unchanged source or policy keeps running; a changed one is replaced. Replacing the flow source the anomaly detector was built with is refused. Probe workers, rate, dispersion, indirect probing, the announcer, providers, probers, `more_specific`, and `synthesize` stay restart-only and are refused by name. A mix is refused whole. An invalid file is refused before anything is applied. The audit log records each apply and each refusal (`config.reload`).

Entering inject online runs the same inject checks as a start and can only succeed when the community, local preference, announcer, and neighbors were already valid, because changing those is still a restart. The announcer's mode, allowlist, and cap change only after the plugins swap, so a refused reload never announces. When `inbound` is configured, `max_improvements` is restart-only: inbound shares the cap and reads it at start, so a reload that changes it is refused by name.

`inbound.mode` and `mitigation.mode` also apply online (#233), with `hold_time`, `improvement_ttl`, and the allowlist reaching the inbound controller; leaving inject withdraws both under their locks, and every other `inbound` or `mitigation` key stays restart-only. The learned-RIB check, community, NO_EXPORT, and withdraw rules are unchanged. A prefix that is not in the learned RIB is never announced. The FRR lab (`lab/e2e.sh`) lowers the latency threshold and the route stays, sets the cap to 0 and the route withdraws, then restores the file and the route returns. `lab/e2e-ix.sh` still covers neighbor reloads.

Lab-proven only, not on a public edge. Rollback: revert this change; a SIGHUP then applies only `bgp.neighbors`, and any other key is refused until a restart.

Outbound local preference (#132 part 1) is the global `local_pref` unless `local_pref_cause` names the improvement's cause or the chosen provider sets `providers[].local_pref`. The provider wins over the cause, and the cause wins over the global value. An empty cause is `performance`. `0` is rejected in every mode, the same rule as a global `local_pref` of 0 in inject: the operator sets each value above the edge's native local preference. The edge import must not rewrite it ([routers.md](routers.md#local-preference-on-import)). A cause change replaces the route already on the wire. Learned more-specifics use the improvement's resolved value. Every move still goes through Decide. Observe stays the default. Rollback: remove `local_pref_cause` and any `providers[].local_pref` and restart.

Extra outbound communities (#132 part 2) are optional. `communities_cause` lists extras for `performance`, `static`, `commit`, and `cost` (an empty cause is `performance`). `providers[].communities` lists extras for routes steered to that provider, added after the cause's. Both are added to `packeteer_community`; they do not replace it. `packeteer_community` and each extra may be a standard community or a large community (`global:data1:data2`, RFC 8092). A list holds at most 16. Duplicates, a copy of `packeteer_community`, and well-known standard communities (`0:x`, `65535:x`) are rejected on extras.

The export policy and the edge import match only `packeteer_community`, standard or large; an extra never matches by itself. A path carrying that community is ignored in the iBGP RIB and over BMP, so a reflected route does not keep its prefix learned. The edge can map an extra to weight, a VRF, an interface, or QoS ([routers.md](routers.md#extra-communities-on-import)). A cause change replaces the route. Learned more-specifics copy the improvement's community list.

The FRR lab (`lab/e2e.sh`) checks `64512:666`, the performance extra `64512:100`, the provider extras `64512:200` and large `64512:1:50`, and `no-export` on the edge, and checks those extras are gone after SIGTERM and after SIGKILL. Lab-proven only, not on a public edge. Field-proven: no. Rollback: remove `communities_cause` and any `providers[].communities` and restart; routes go back to `packeteer_community` and NO_EXPORT only. A large `packeteer_community` also needs the edge import and eBGP filters changed back to the standard community, then a restart.

More-specific injection (#56, [design](design/more-specific.md)) is off unless `more_specific.enabled: true`. An improvement on P then also announces each prefix strictly inside P that a neighbor advertises exactly in the learned RIB (inside the allowlist, not held by inbound or mitigation), toward the same provider, with that improvement's resolved `local_pref`, community, and NO_EXPORT. Nothing is split or computed; `more_specific_bits` is still rejected. `more_specific.max_routes` (default 100, at most 1000) caps routes on a router, not decisions: improvements, their more-specifics, and inbound steer routes.

A new improvement is announced whole or not at all, a later more-specific only while there is room, and nothing on the wire is withdrawn to make room. A more-specific is withdrawn with its improvement, on a confirmed RIB leave (advertised 5s, then gone; a best-path hide is kept), on RIB loss, SIGTERM, and with the session on SIGKILL. The FRR lab (`lab/e2e-more-specific.sh`) asserts on the edge the exact route set and count at every step, that no unlearned more-specific appears, the cap holding a second improvement back, a real `no network` withdrawing a more-specific and freeing room, SIGTERM, and SIGKILL.

Lab-proven only, not on a public edge. Rollback: remove `more_specific` and restart.

Multiple routers (#27, first half) are `bgp.neighbors` entries with optional `providers` (the transits a router forwards to itself; it is their egress) and `next_hops` (providers it reaches through another router, and the next hop it uses). The `gobgp` announcer installs a per-router export policy on the single speaker: a route toward a provider the router cannot reach is not sent to it, and one it reaches through another router is sent with that next hop. A neighbor with neither list gets every route, so single-router and route-reflector configs are unchanged.

When every egress session of a provider is down, the provider is unusable (`egress router down`): no new improvement, and an active one is retired at once and withdrawn from every router. One session dropping removes only that router's routes; all sessions down withdraws everything. The learned-RIB, allowlist, community, NO_EXPORT, cap, and hold-time rules are unchanged; inbound steer routes are not affected. Route reflectors are a neighbor with no lists, Packeteer is a reflector client, and every edge resolves the provider next hop ([route-reflector.md](route-reflector.md)).

The FRR lab (`lab/e2e-multirouter.sh`: two edges, a reflector, two transits) proves per-router next hops, one edge's session loss leaving the other steered, egress-router loss withdrawing everywhere, the reflected steer on both edges, SIGTERM, and SIGKILL. Lab-proven only, not on a public edge. Rollback: remove `providers`/`next_hops` and restart, or point `bgp.neighbors` at a single router.

Internet exchanges (#27, second half) are an `exchanges` list. Each peer is a provider with its own `next_hop` on the peering LAN, its own probe `source_ip`, and its AS. A peer carries only its own routes, so it is always route-checked: no improvement goes to it unless the router shows Packeteer the peer's own path for the exact prefix (first AS = the peer's `asn`), through iBGP add-path or BMP, and an active one is retired at once when that path goes; with no visible path the check fails closed. An exchange name in `bgp.neighbors[].providers` or `next_hops` stands for all its peers.

Exchange statistics are live on `/api/exchanges` and `packeteer_exchange_*`: per peer, the prefixes seen through its next hop, a mismatched observed AS, probe health, and active improvements; and next hops on the peering LAN that are not configured (`discovered`), which are never probed or used. A peer is not assumed to be a route server (#146). Probe targets whose prefix is inside an exchange LAN are dropped (#145). A flow or span destination on a peering LAN is not aggregated into a probe prefix, and a pinned host on a LAN is not probed. Traceroute does not adopt a hop on a LAN. `allowlist.prefixes` may not overlap a LAN. Each peer's next hop is probed from its `source_ip` every probe interval and `exchange.degraded` fires when enough peers fail it inside a window (#149; [CONFIG.md](CONFIG.md#exchanges)).

`packeteer_exchange_lan_targets_dropped` counts the omissions. Nothing is announced. Each learned path carries `via`: `route_server` when a BMP neighbor on the exchange LAN is not the path's next hop (the MED label names that neighbor), `bilateral` when the neighbor is the next hop, and `unknown` on an iBGP add-path or Loc-RIB path until BMP paths for the same next hop agree. `/api/exchanges` shows the same value per peer, `unknown` when the paths disagree or none have been seen. MED stays display-only. Per member, `availability` counts prefixes seen only via a route server, only bilaterally, or both, from BMP Adj-RIB-In paths, and flags `rs_partial` or `rs_missing` (#156). The route check is unchanged. The offload report (#152) lists, by bytes, the prefixes whose exit is a transit while a configured peer passes the route check for the exact prefix; it announces nothing and steers nothing. The potential-peers report (#154) ranks destination origin ASNs by bytes and says whether an exchange member carries each AS and whether its prefixes have a path through an exchange LAN; it opens no session and announces nothing. The BMP session monitor (#147) decodes each peer's Statistics Report Adj-RIB-In count and its session events: `exchange.peer_up`/`exchange.peer_down` carry the RFC 7854 reason (Cease subcode 1 is the peer's max-prefix limit), `exchanges[].max_prefix_warn_pct` of `peers[].max_prefix` raises `exchange.max_prefix` and `exchange.max_prefix_cleared`, and `/api/exchanges` carries `adj_rib_in` with `packeteer_exchange_peer_adj_rib_in`. Read-only; no route changes.

`bgp.as_path` sets the AS path on injected routes: `empty` (default, as before), `native` (the learned route's), or `provider` (the chosen provider's own learned path, else native); Packeteer never prepends its own AS. Online reconfiguration: SIGHUP reloads the file and applies `bgp.neighbors` to the running speaker. Sessions are added and removed without touching the others, a changed per-router table replaces the export policy (outbound routes are withdrawn first and announced again under it), and egress routers are recomputed.

Thresholds, hold time, the improvement cap, policies, sources, probe timing, mode, and the allowlist also apply on that SIGHUP (#128). A restart-only key, or an invalid file, is refused with the keys named and the running config stays. A failure after the speaker changed stops Packeteer, which withdraws everything. The learned-RIB, allowlist, community, NO_EXPORT, cap, and hold-time rules are unchanged.

The FRR lab (`lab/e2e-ix.sh`: one edge, a transit, three exchange members on a simulated peering LAN, and a second iBGP router) proves the steer onto an inactive exchange path with that peer's next hop and AS path, the route check keeping the fastest peer (no route for the prefix) and an unconfigured member unused, the exchange statistics, the route-check withdraw and re-steer, a SIGHUP that adds a router without resetting the edge's session or dropping its route, a refused restart-only reload, a SIGHUP that removes the router, SIGTERM, and SIGKILL. Lab-proven only, not on a public edge.

Rollback: remove `exchanges` and `bgp.as_path` and restart; online reconfiguration needs no rollback (a restart ignores it).

Multi-POP (#30, [multi-pop.md](multi-pop.md)): one Packeteer instance per POP (routing domain), joined by a `federation` plugin. The built-in `mtls` plugin serves each instance's snapshot over HTTPS with mutual TLS 1.3 (certificates from a mounted CA; unknown client certificates get 403) and polls its peers; it never announces or decides. A snapshot carries the instance's own providers (health and telemetry), its fresh measurements through them, how its traffic for each learned probed prefix leaves, and its improvements.

A provider with `domain` set to another POP is not probed locally: its path is the peer's measurement plus the configured `inter_dc_rtt`, and it is usable only while the peer is fresh, its RIB is ready, it reports the provider up, and its own traffic for that exact prefix leaves through that provider (so traffic cannot loop between POPs; two simultaneous steers at each other are broken by domain name). Rollback: remove `accept_settings_from` and restart; revert an applied push like any config edit.

Threat mitigation, first half (#28): RTBH and BGP redirect. A new `mitigation` block with its own `mode` (default `observe`, a dry run), its own `allowlist`, `max_rules` (default 10), and `default_ttl`/`max_ttl` (1h/24h, at most 168h), and a new in-process mitigation announcer (`mitigation.announcer`, type `gobgp`) with a marker community, a blackhole discard next hop and communities (RFC 7999 `65535:666` by default), and named redirect targets. Operators add and remove rules through `POST`/`DELETE /api/mitigations` (basic auth).

In `inject` each rule's exact prefix is announced to the edge on the existing iBGP session with the action's next hop and communities, `packeteer_community`, the marker, and NO_EXPORT, only while the prefix is in the learned RIB; the announcer re-checks the allowlist and the cap itself. Rules are in memory only (a restart drops them: no stale intent) and always expire; removal, expiry, RIB loss, and shutdown withdraw, and a crash drops the routes with the session (no graceful restart). A prefix a rule holds is withdrawn from outbound improvements and inbound steers first.

The edge opts in by matching the marker and routing the discard address to null ([mitigation.md](mitigation.md)). The FRR lab (`lab/e2e-mitigation.sh`) checks on the routers: refusals outside the allowlist and past the cap, an allowlisted more-specific not in the RIB never announced, RTBH in the edge's BGP table and FIB with nothing leaked to the other transit, redirect in place, DELETE, TTL expiry, SIGTERM, no rule after a restart, and SIGKILL. Lab-proven only, not on a public edge.

Threat mitigation, second half (#28): FlowSpec, country policies, monitor, feed, and history. The mitigation `gobgp` announcer's `flowspec` block enables `flowspec_drop` (traffic-rate 0), `flowspec_rate_limit` (`rate_mbps`, sent as bytes per second), and `flowspec_redirect` (named two-octet-AS route targets); with it and `mitigation.mode: inject`, the iBGP sessions also offer the IPv4/IPv6 FlowSpec families (RFC 8955).

A FlowSpec rule's destination is the rule's exact learned prefix and it may be narrowed by `source`, `protocols`, `destination_ports`, and `source_ports`; `source_countries` expands, when the rule is added, to merged networks from a MaxMind-format database the operator mounts (`mitigation.geoip_db`; none shipped), one FlowSpec rule per network. Every FlowSpec rule carries `packeteer_community`, the marker, and NO_EXPORT, is announced only while the destination is in the learned RIB, and counts toward `max_rules`, which now counts routes; the announcer re-checks the allowlist, the community, and the same cap over RTBH, redirect, and FlowSpec.

FlowSpec does not replace the unicast route, so it does not hold the prefix against improvements. TTL, removal, RIB loss, shutdown, and a crash (no graceful restart) withdraw it as for RTBH. Monitor, rules, feed, and history: the dashboard's read-only Threat mitigation section and `packeteer_mitigation_*` metrics; the rules API; a feed of the last 200 changes on `GET /api/mitigations` and as `mitigation.added`/`announced`/`withdrawn`/`ended` events to every notifier; and stored history (`sqlite` `mitigations` table, `/api/reports/mitigations` with CSV).

Packeteer has no external threat-intelligence feed ingest; a detector adds rules through the API (automatic detection is #33). The FRR lab (`lab/e2e-mitigation.sh`, with a lab GeoIP database from `lab/mkgeoip`) checks in the edge's FlowSpec table: a non-learned prefix never announced, a country drop as one rule per network, nothing on the other transit (NO_EXPORT), the cap counting routes, a rate limit replacing the drop in place, DELETE, a redirect route target, SIGTERM, and SIGKILL. It checks the control plane; FlowSpec enforcement in the edge's data plane is the router's. Lab-proven only, not on a public edge.

Rollback: `mitigation.mode: observe` (or remove `flowspec`/`mitigation`) and restart.

Automatic traffic anomaly detection (#33, [anomaly.md](anomaly.md)): the `flow` source counts bytes per destination prefix and IP protocol (`plugin.FlowCounterSource`); on its own `anomaly.interval` the core turns the deltas into rates and feeds a `detector` plugin. The built-in `baseline` detector keeps an EWMA mean and variance per key and reports a key once it is `sensitivity` standard deviations, `min_ratio` times, and `min_mbps` above its baseline for `trigger_rounds` (or past a static `max_mbps`), and clears it after `clear_rounds`; attack rounds are not learned.

Every anomaly is logged, listed with a 200-entry feed on `GET /api/anomalies`, sent as `anomaly.detected`/`mitigated`/`held`/`cleared` events, counted in `packeteer_anomal*` metrics, and stored (`sqlite` `anomalies` table, `/api/reports/anomalies` with CSV).

A mitigation rule is added only when an explicit `anomaly.rules` entry matches (prefixes inside `mitigation.allowlist`, protocols, `min_mbps`), only for an exact prefix in the learned RIB, never on an HA standby, never replacing someone else's rule, under `max_active` and `max_actions_per_hour`, and only through the mitigation controller (its mode, allowlist, `max_rules`, TTL, community, NO_EXPORT). The rule is removed when the anomaly clears, and every anomaly clears when flow data fails three rounds in a row.

The FRR lab (`lab/e2e-anomaly.sh`, synthetic NetFlow v5 from `lab/sendflow`) proves on the routers: steady traffic and a 1.6x rise raise nothing; a TCP flood with no rule announces nothing; a UDP flood toward a rule prefix that is not in the learned RIB is never announced; a UDP flood on the learned prefix becomes a FlowSpec drop with NO_EXPORT that never reaches the other transit and is withdrawn when the flood ends; RIB session loss, SIGTERM, and SIGKILL withdraw it; a restart holds nothing. Lab-proven only, not on a public edge. Rollback: remove `anomaly.rules` (alerts only) or the `anomaly` block and restart.

Remaining UI features (#34, [ui.md](ui.md)). **Improvement weights**: the `weighted`, `commit`, and `cost` scorers take an optional `improvement_weights` block (`performance`, default 1; `volume`, default 0). When it is set, new static, VIP, and performance moves competing for the last `max_improvements` slots are admitted by `performance x score gain + volume x Mbps` instead of by gain alone, inside their lane (static pins still first; commit and cost moves keep relief and savings order).

Weights only order moves Decide already accepted: a prefix not in the learned RIB or not allowlisted is never admitted, the cap still binds, an active improvement is never displaced, and every route still carries the community and NO_EXPORT. The weight is on `/api/decisions`.

The FRR lab (`lab/e2e-weights.sh`) proves the heavier learned prefix wins the one slot, a heavier prefix the edge never advertises is never announced, a RIB leave withdraws and hands the slot over, a returning heavier prefix does not displace, SIGTERM, restart, and SIGKILL. **Config editor and first-run wizard**: with `http.config_editor: true` and auth or basic auth, an admin reads, validates, and writes the mounted config file (`/api/config`, `/settings.html`).

A write needs the hash of the file it edits, passes the same checks as a start (loader, environment, every plugin's config, cross-checks), never runs an `exec` plugin and refuses one that is added or changed (or a changed `plugin_dir`), needs `confirm_inject` to turn inject on, is read back through `config.Load`, and is audited by hash. It is not applied to the running controller: restart (or SIGHUP for `bgp.neighbors`).

The wizard (`POST /api/config/wizard`) renders an observe-mode config with an empty allowlist for review in the editor. **Custom dashboards**: per-user layouts of read-only widgets in the `sqlite` store (`/api/dashboards`, `/dashboards.html`).

The improvements widget is titled Recommended improvements outside inject and Active improvements in inject, and widget timestamps use the dashboard's local time (#171). **Settings form**: each provider field (name, probe source, next hop, cost, commit) has a visible label that is the accessible name, and the wizard's three provider fields do too (#171). **Report subscriptions**: `report_subscriptions` email a stored report as CSV on a daily, weekly, or monthly UTC schedule through an `smtp` notifier; `/api/subscriptions` shows their state and operators may send one now.

Reports (#23) come from the `sqlite` storage plugin, which is on when `storage` is set (the example config sets it) or when sign-in defaults on (#328), and off otherwise. It keeps daily probe rollups per prefix and provider, one row per improvement with the native and chosen provider's loss and RTT at the decision, and per-prefix origin ASN, country (from a `rules` policy with `geoip_db`), and volume.

`/api/reports/<name>` serves `summary`, `improvements`, `exchanges`, `causes`, `performance`, `providers`, `prefixes`, `asns`, `countries`, `probes`, `savings`, and `timeseries` (#129, per-day before/after loss and RTT for the all, problem, 20%-better, and 50%-better buckets) as JSON or CSV, and the dashboard shows them. `/graphs.html` and the `timeseries` dashboard widget draw `timeseries` as charts ([ui.md](ui.md#graphs)). Mount `/var/lib/packeteer` so history survives a restart. The recorder writes once a minute and never blocks a decision or a withdraw; it does not announce.

Push exporters (Prometheus remote-write, OTLP) are not built: scrape `/metrics`.

Users, RBAC, access restriction, and the audit log (#32, [auth.md](auth.md)) gate the ops HTTP server unless `auth.enabled: false` is written (on by default since #328; the first admin password is generated when none is set). Roles are `viewer` (read, own API tokens), `operator` (maintenance windows, mitigation rules, troubleshooting tools), and `admin` (users, audit log); every route has a minimum role, checked by one middleware, and a test walks every route with every role. Users and API token hashes live in the storage plugin (`plugin.UserStore`, implemented by `sqlite`); the first admin comes from `PACKETEER_ADMIN_PASSWORD` or a generated password that must be changed at first sign-in.

Optional single sign-on is the `sso` plugin kind with the built-in `oidc` (code flow + PKCE, verified ID token, groups mapped to roles). `http.allow_from` restricts client addresses; failed sign-ins are throttled; cross-site browser changes are refused. Every change, denied change, SSO sign-in and sign-out, and config reload is written to the log, the store (`plugin.AuditStore`, `/api/audit`), and the notifiers (`audit.recorded`). Troubleshooting tools (#24) live on the ops HTTP server. The looking glass reads the learned RIB view (exact route, longest covering route, more-specifics) and is always on. With `troubleshoot.enabled`, an on-demand probe runs the prober chain from every provider source, a UDP traceroute runs from each provider source, and whois goes through the `rdap` whois plugin. Requests are `POST` with JSON, rate limited, and behind basic auth when it is on. On-demand results are returned to the caller only and never reach the probe engine or the decision loop; nothing announces.
